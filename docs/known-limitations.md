# Known limitations

This is an experimental, single-host plugin. The current compatibility tests do not establish that all collaboration, isolation or acceptance problems are solved.

This page lists the limitations that are true of the current tree, one section per gap. It is not a history: [validation.md](validation.md) records each round and its evidence (its round-28 and round-29 entries list the items this page dropped as resolved that no other entry records), and the round-by-round text of this page (including rounds 13-17, which validation.md does not record) is in git history at `fa6a507` (`git show fa6a507:docs/known-limitations.md`).

## Supported Harness versions

- **Supported hosts (round 28).** Exactly two Harness releases are supported: `0.1.5-rc.3` (npm `latest`, the default host, `a4c74a91e06b00fe0b0937bde982170c526cc842`) and `0.1.7-rc.1` (npm `next`, `46a7f68b0922371ce7144b668b90e377d8e799f4`). `0.1.2-rc.1`, `0.1.3-alpha.2`, `0.1.5-rc.1` and `0.1.6-alpha.2` are no longer supported, and the code that served only them (the standalone dock, the `agentCtx.agent` setup fallback, the single `deployment:persona` section, the persistence `list` fallback) is deleted. Validation entries before round 28 record checks against those earlier releases. With neither `DSH_HARNESS_ROOT` nor `DSH_SOURCE` set, the scripts and the fault suite take the first checkout among `~/.dsh/source/current` and the sibling `deepseek-harness-015rc3`/`deepseek-harness-017rc1` directories whose version is supported and whose CLI entry `apps/cli/lib/bin.js` is built, and skip any other; the sibling names are a development convention, not a discovery mechanism. The built check is that one file, so a checkout whose CLI is built but whose other packages are not is still chosen and fails later, while its packages load.
- **The panel is a native right-sidebar tab on both hosts, and the right sidebar belongs to one conversation.** Opening a worker's conversation from the panel navigates natively, but that conversation's right sidebar starts closed; the read-only swarm view appears after the user presses the Agent Swarm launcher at the bottom of the left navigation. There is no plugin-owned dock any more, so a profile without the host right sidebar (and without Better Sidebar) has no swarm panel; its geometry, collapse and narrow-screen layout are the host's. The dock residuals recorded for the 2026-09-11 C3 fix (host root discovered from the dock, inline-style shift) no longer apply.
- **Host editor defect on both supported releases (not fixed by installing the plugin).** In `@deepseek-ai/dsh-client-ui-conversation` (`src/client/input/editor/claim-decor.ts`) the claim-token transform splits the styled `/command ` token with `splitText`; the overflow keeps the token style, Lexical merges the identically styled siblings, and the transform never settles (`One or more transforms are endlessly triggering additional transforms`). It reproduces headlessly on 0.1.5-rc.3 and 0.1.7-rc.1 (and 0.1.6-alpha.2) when text is appended to the styled token node. `patches/harness-command-input.patch` clears the overflow style after the split and `scripts/check-harness-command-input.mjs` verifies it against either supported checkout, but applying it requires a rebuilt `ui-conversation` loaded through a preview overlay. The browser command smokes pass on the stock hosts; an operating-system IME path was not tested.
- **Round-28 coverage limits.** On both new hosts the gates cover typecheck, build, the behavioral suite, the real Loader composition, the packed artifact, the CLI profile, the bundle tests, the fault suite and the two browser smokes with a scripted model. `test:replay` reproduced `sha256:61a921e64088b78b957cd6aeaa563d5436d4a6eae4b0130725d1f3c74c6f971e` with the plugin linked to 0.1.5-rc.3. A real-provider mission (`test:deepseek`, `test:command-deepseek`), `test:load`, Better Sidebar and the attended preview were not exercised on 0.1.5-rc.3 or 0.1.7-rc.1.
- **Every entry point refuses another release, even one named explicitly.** `test:harness`, `test:pack`, `test:profile`, `test:bundle`, `test:web`, `test:command-web`, `test:deepseek`, `test:command-deepseek`, `scripts/check-cancel-freeze.mjs`, the fault suite, `scripts/start-lab.mjs`, `scripts/start-preview.mjs` and `npm run link:dsh` stop with `Unsupported Harness <version>; supported: 0.1.5-rc.3, 0.1.7-rc.1` for any other release, and also require the release commit that `compatibility.json` records. The fault suite checks once, before any scenario, when F3a/F3b/F3c are selected. `scripts/update-preview.mjs` and `node scripts/round.mjs mount` refuse the same way before building, unless `--allow-unsupported-harness` is passed; mount forwards that flag. They then continue with a warning on stderr and in `restart.log`. The override exists for a preview that still boots an unsupported release from a snapshot linked to that release's SDK packages; such a preview is updated only on that explicit choice.
- **Only 0.1.7 hosts enforce the supported releases; elsewhere the plugin only logs.** The 0.1.7-rc.1 compatibility preflight disables a plugin whose `@deepseek-ai/dsh-*` peer ranges do not admit the host. 0.1.5-rc.3, like 0.1.6-alpha.2, has no peer-version gate, and neither host reads the profile bundle's `dsh.bundle.requires.harness`, which stays declarative. On every host, `apply()` reads the version of the `@deepseek-ai/dsh-session` package the plugin resolves. When that version is neither `0.1.5-rc.3` nor `0.1.7-rc.1`, it logs the error `agent-swarm: Unsupported Harness <version>; supported: 0.1.5-rc.3, 0.1.7-rc.1. The plugin still loads but is untested on this host; run it on a supported release.` and keeps loading. An unreadable version logs a warning, and nothing is refused. The version is that of the SDK package the plugin loads. In a profile install that is the host's own package; a plugin checkout linked with its own `node_modules` reports the release those links point to.

## Scope: one host, one writer

- **Single-host, single-writer.** Admission, lease and budget accounting is durable but scoped to one host and one writer process: every mutation serializes through one SQLite writer connection. A competing writer is classified as `writer_busy` and retried with bounded backoff; progress is not guaranteed under sustained contention. Each `SwarmRuntime.commit` is one SQLite transaction and writes nothing after it commits (the owner notices it triggers are published later, in their own transactions), so a claim refused as `writer_busy` wrote nothing. Two writers against one store file, or one store shared across hosts, are unsupported; multi-host scaling needs external coordination and is out of scope.
- Separate hosts must configure distinct `statePath` and `workspacesRoot`. The plugin defaults (`~/.dsh/agent-swarm/…`) ignore `DSH_HOME`; the profile bundle uses `$DSH_AGENT_SWARM_ROOT`, else `$DSH_HOME/agent-swarm`. A live owner's lock normally rejects a second host, but stale-lock reclamation is a read/check/unlink sequence, so simultaneous recovery processes can race; the process birth check distinguishes PID reuse without making reclamation atomic, and unknown or legacy live identities stay conservatively locked. Do not start or restore several hosts against one state path.
- Windows execution, distributed workers and non-Git projects are unsupported. Declared checks and the syntax probe execute through `/bin/sh`, and delivery relies on POSIX link/`lstat` semantics.

## Harness integration

- **The plugin writes no plugin-owned event into a session log and owns no session projection.** Its only direct session appends are the host's own `sandbox/mode` and `approval/policy` events, which each worker activation writes to that worker's session, never the owner's (`src/harness-workers.ts`); `tests/r17-projection.test.mjs` requires every `session.append` in `src/*.ts` (the client sources under `src/client/` are not scanned) to name a literal type from the host's `KNOWN_SESSION_EVENT_TYPES`. The host's session vocabulary is closed (`KNOWN_SESSION_EVENT_TYPES`) and a log carrying an unknown type fails to decode (`SessionFormatUnsupportedError`) unless its envelope is `ignorable: true`, which `Session.append()` cannot set. The board is derived from `swarm.sqlite` on demand, so the client reads it only through this plugin's RPC/live path and no host projection key carries it.
- Swarm tools are registered globally and hidden per session by role (entry, management, member, or none for subagents). Hiding is presentation through the host's scoped restriction; the runtime guard and owner checks remain the authority boundary. A session's cached prompt prefix changes once, when it becomes an owner.
- Managed-worktree Git plumbing, the shell-syntax probe and every declared check spawn through the host subprocess service (`ctx.subprocess`), which owns TERM-before-KILL escalation and host-exit termination; delivery Git operations (`execFile` in `src/delivery.ts`) and the store's lock-owner birth check (`ps` via `execFileSync`) do not. Without a subprocess provider a managed command is refused with `[subprocess_service_required]` (the base profile always mounts one). The provider creates a spill directory under the ambient temp root on every spawn, so an uncreatable `TMPDIR` fails a command inside the host before any plugin fallback (fault scenario F8).
- Every `WorkerAdapter` method except `prepareBaseline` and `checkEnvelope` is required; a JavaScript adapter that skips type checking and omits one fails with a TypeError. An operation counts as live only while the adapter's `currentActivity` confirms the durable activity, and `[delivery_unsupported]` comes only from an adapter that throws it.
- A non-cooperative native operation stays fenced until it settles (it is not charged again as a startup failure), and an adapter teardown that cannot finish within its cleanup bound reports failure rather than claiming every handle was released.

## Tool authority and tool schemas

- The worker guard is a name-based deny list, not a capability allowlist. Other profile tools, including scheduling tools such as `cron_add`, may have external effects it does not cover. No separate network/credential policy or adversarial multi-tenant isolation is provided.
- Workers cannot write git metadata: a member worktree's index, refs and `.git/worktrees/<name>/` live under the shared common directory outside the writable path, so worker `git add`/`git commit` fails with `index.lock: Operation not permitted`. The worker gets a typed error naming `swarm_submit` before its next model step; publication is host-side capture.
- Tool calls are checked against their schema: required properties, enums, primitive types, `oneOf` and undeclared keys are refused with `[tool_arguments_invalid]` naming each path and the accepted keys, so a model that adds an undeclared key needs one retry. Numeric minimums stay runtime checks. JSON null on an optional property is an omission, except `swarm_control` `changes.assigneeId`, where null or an empty string releases the binding. `swarm_launch` ignores a top-level `workspace` and uses the frozen request workspace.
- Advice that names a role-hidden tool (for example `swarm_budget` or `swarm_cancel`, which a worker cannot call) is phrased for the mission owner rather than the caller; the refusal lint has no role-aware check.
- The owner protocol is at its prompt budget: `tests/roles.test.mjs` caps `OWNER_PROMPT` below 5,531 characters and it is 5,476 at `73cf4fb` (`WORKER_PROMPT` 1,507 of 1,600). A new protocol sentence must replace one, or state something no tool schema description can carry.

## Workspace authorization

- **Authorized per-mission workspace (human-only authorization surface).** A mission may target a repository outside the calling session's cwd only when it resolves inside a root configured in `authorizedWorkspaces`, loaded once at plugin start from the profile/`cordis.patch.yml`. No model-callable tool can create, widen or revoke a root; a change needs a human edit plus a host restart. Containment is decided on `realpath`-resolved path components. The matched root is recorded (`mission.workspaceGrantRoot`, `mission/workspace-bound`, `workspace/grant-loaded`). Each entry point (the `swarm_stage`/`swarm_create` workspace binding, the browser draft API, the `/agent-swarm` command) hands the runtime that authorization beside the plan, never inside it, and the runtime records the configured root that contains the workspace, never a wider one the caller names. One rule (`claimFor` in `src/authorization.ts`) decides admission and every re-check: the calling session's own directory, else the most specific configured root, still active, that contains the realpath-resolved workspace. Only the runtime re-checks a recorded workspace, on the runtime clock: before every worker start, member admission, task preparation (claim and dispatch), planning snapshot, plan repair, draft launch (before its check preflight) and delivery inspection or application, and before each verification checkout, the declared-check retry included. Submission capture, a review's artifact inspection and capture, and the checkpoints taken at a stop, an idle close-out or a lease expiry inside a running attempt have no re-check of their own: they write objects and refs into the authorized repository until a re-check on one of those paths fences the mission, which blocks and stops its running work. The runtime's grant snapshot (`RuntimeConfig.grants`) is required and is the only one every entry point and re-check reads; a plugin with no configured root loads the empty snapshot, which authorizes only the calling session's own directory. The worker adapter holds no grants. Removing a root and restarting therefore refuses new missions and fences a running one with a durable blocked reason and a `[workspace_terminal]` owner notice. A grant whose `expiresAt` passes, or a workspace that stops resolving, while work runs fences that work at the next scheduling pass, not at its next preparation. Adding or removing a nested root never fences a mission that a configured root still contains. Each fence that blocks work records `mission/workspace-revoked`, so work resumed before the root is restored is fenced again; a submission whose review the fence blocked still gets one automatic review per review need, and the next dispatch fences each such review with its own `mission/workspace-revoked` row and task slot, so a challenge on a fenced mission adds one of each. The `[workspace_terminal]` request is told once per plugin runtime (each Harness start or plugin reload) that finds the mission revoked: within one runtime, however the board moves or the work is resumed and fenced again; a restart that finds it revoked again, whether or not the root was restored and the work ran in between, tells it again and records one more `mission/workspace-revoked`, whose `blockedTasks` may be empty. The request names the work the fence blocked at its new epochs (the mission root when it blocked none), and the board classifier tells that stuck work in its own words too, the stall root of each blocked task and, when nothing else can run, the W3 stall, so one revocation wakes the owner with three or more wordings of one condition (the open item R20 under owner notices); the compact panel's three newest events are then those facts' `mission/stalled` rows, and the revocation is read in the Activity view. A mission, draft or automatic request recorded without an authorization source (by a build before `workspaceAuthorizationSource` existed) is judged by the configured roots alone: if none contains its workspace, a mission is fenced, and a draft's launch or a request's planning snapshot is refused with the revocation diagnostic, even when it was recorded from a session cwd. Workers can never create a mission or use a grant.
- Residual risks: **(1)** a model running with full filesystem access on the host could edit the plugin configuration file to add a root (a restart is still required), which is why the target design is a human-only command surface (`/swarm-workspace add|remove|list`) that tool calls cannot invoke; **(2)** the containment check and the following git operation are separate syscalls, so a root replaced by a symlink or remounted in that TOCTOU window is not caught; **(3)** authorization is write/execute authorization, **not confidentiality**: an authorized root can hold secrets the swarm may read.

## Isolation and sandbox

- **Isolation invariant.** The board function `isolationIssues(board)` (`src/board.ts`) requires every non-stopped member to have its own provisioned worktree and two running tasks sharing a worktree to declare disjoint scope; dispatch checks it before starting a member and after `prepareTask`, and a violation leaves the task pending and wakes the owner with one `[workspace_terminal]` decision per distinct violation, which names the unfinished work of every member the violation lists when it is first told and is outstanding (delivered, reminded) while the invariant still lists it. The dispatch question is asked beside it about each task the violation keeps from dispatching, once per task epoch (one more wording of the open item R20), so work given later to a listed member, or runnable only by listed members, which the request does not name, is named too. A listed member's blocked task is named by its stall root beside the request. A violation whose text recurs after a repair (the same member ids and worktree path or task ids) is the same decision: its row is outstanding again, but only its unspent reminders (at most two over its life) speak. Disjointness is asserted only inside one worktree; tasks in distinct worktrees are isolated by construction, not serialized.
- Declared scopes are checked when artifacts are captured; they are not per-shell-write allowlists.
- **Shared temp roots are a cross-member channel (R11-15).** The workspace-write policy also allows writes under `/tmp` and `os.tmpdir()`, shared by every member and mission on the host, so two members can rendezvous through a well-known temp path; the channel is not confined and contents are not attributable. Detection is a heuristic over host-recorded tool input naming `/tmp`, `/var/tmp` or `os.tmpdir()`: two members naming one path within `TEMP_RENDEZVOUS_WINDOW_MS` (10 minutes) write an `isolation/temp-rendezvous` event once per pair and window, and wake the owner once per path and pair of tasks at their epochs (the path is the notice's reason). It proves no write, scans no directory, and keeps its mention history in process memory (2,048 paths, 8 mentions each), so a restart forgets it. A hard boundary requires removing those roots from the sandbox policy. Recorded open, not re-verified at `fa6a507` (R17-G15): a shared temp path and a path inside another member's attempt scope are reported identically.
- The member scratch root is `<member worktree>/.swarm-scratch` (the adapter's `TMPDIR`/`TMP`/`TEMP`), excluded like a dependency directory and never materialised into a verification checkout. It lives in the retained worktree, so its contents survive stop/completion and are never collected. A composition persisted with the round-16 sibling root is accepted on resume and rewritten; any other root is refused.
- Worker sessions confine every bash/tool call with the mission's sandbox mode, so a real Loader composition driven from inside a worker fails with `SANDBOX_UNAVAILABLE` even on a healthy host. The fault suite's provider-fault tier (F3a/F3b/F3c) therefore registers an identity sandbox provider and an unsandboxed `bash-local` shell; its invariants do not depend on OS confinement.

## Declared checks and verification

- Independent host verification proves that the declared checks ran against the exact artifact, not that they are meaningful. Initial automatic checks come from the primary, participants can propose others, and no mission-wide acceptance baseline is imposed on every artifact. Accepted history is not re-reviewed after an upgrade.
- Whether an artifact needs host checks is a file-format rule, not program analysis (`src/artifact-policy.ts`): whatever the task kind, an artifact with an executable path, or with a changed file outside the report extensions (`.md`, `.markdown`, `.txt`, `.rst`, `.adoc`, `.pdf`, `.csv`, `.tsv`, `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`) and README/LICENSE-style names, is refused without checks (`[artifact_checks_required]`). Literal no-op checks are refused (`[check_noop]`); any other always-passing check is left to the reviewer.
- An acceptance without declared checks needs only one non-error host-recorded tool run by the reviewer on that attempt, so independent reproduction of a research result is encouraged, not required.
- **Host-absolute paths in checks (`[check_absolute_path]`).** Admission refuses a check naming an absolute path outside `/bin`, `/usr/bin`, `/sbin`, `/usr/sbin` and the four standard `/dev` streams, or any absolute path inside the mission workspace, because checks run in a fresh verification worktree under a random path. The scanner is a bounded POSIX-ish tokenizer (quotes, escapes, doubled slashes, `.`/`..` segments, quoted, backtick and `eval` bodies and `PATH`-style lists are resolved; `<scheme>://…` values are admitted), not a shell parser. Residuals: a candidate containing any of `^ $ [ ] ( ) ? + { } | * \` counts as a pattern and is admitted (a glob such as `/Users/*/secret` passes), as do separators (`awk -F/`) and `/word/` regex literals; home-relative paths (`~/.local/bin/uv`, `$HOME/…`), ANSI-C quoting (`$'\x2f…'`), `file://` URLs, `$IFS`, `$(…)` output that is not a literal path word, `${VAR}` indirection, aliases and functions are not resolved; and a check can rely on mutable host state the clean checkout shares.
- A declared check that changes on replacement or re-submission is recorded (`task/check-changed`, previous and new checks), not refused. A re-submission keeps the stored check, but a replacement can declare a weaker relative command. Supplying checks a task never declared is not a change.
- Admission detects one host requirement only: a nested sandbox invocation (`sandbox-exec`, `dsh sandbox`), written directly or reached through a chain of up to five nested `npm run` scripts (a sixth is not followed), is refused with `[check_requires_host]`. Any other host capability a check needs (a built Harness checkout, a browser, network) fails at verification; an unresolved `npm run` name is only a preflight hint.
- Launch preflights checks only for shell syntax (`/bin/sh -n`, `[check_syntax_invalid]`, on every launch path). A check is not run against its task's composed base or inside the execution sandbox beforehand (recorded open rows R17-G16, R17-G17), so a check that cannot pass there is found at verification.
- **Verification dependencies.** Verification checkouts materialise gitignored dependency directories instead of installing: `node_modules`, `.venv`, `venv`, `vendor` and `.tox` by default (`DEFAULT_VERIFICATION_DEPENDENCY_DIRS`; `verificationDependencyDirs` replaces the set, `[]` disables it), matched as a path component at any depth. A check therefore runs against committed files plus an installed toolchain that is not part of the artifact and may differ from a fresh install; build outputs and other ignored paths are never provided. Checks run sandboxed in the disposable checkout, refused unless the host reports **full** enforcement (F-29). The effective mode is copy: the schema default `verificationDependencyMode: 'link'` is honoured only with `allowDependencyLinkReads: true`, because a read-through link lets `..` reach the source checkout and F-29 governs writes, not reads (R11-13). Copy mode copies a link to an external regular executable (a virtualenv interpreter) as an executable file, but system libraries may still be needed; broken or cyclic links, links into other source-checkout content and external directory or non-executable links defer the review as an infrastructure failure (`(verification preparation)`, exit 125) after one retry; such layouts need a self-contained installation or the link-read opt-in. Concurrent copies are bounded by running verifications, not `checkConcurrency`. This is not a hermetic toolchain, and an unconfined `Workspaces` (the identity `confineCheck` unit tests inject) has no boundary at all.
- **Deferred verification has no bound.** A declared check that decides no verdict defers the review instead of rejecting the source, with its kind recorded on the check row where the row is produced: `timeout` (the host's own check deadline fired; stored as exit 124), `infrastructure` (the host could not prepare, confine or start the check, exit 125, including a host git deadline while it proves the artifact or creates the checkout) or `unrunnable` (exit 126 or 127: the command could not run in the clean checkout). A command's own exit 124 (an inner `timeout`, or `exit 124`) is an assertion failure and rejects the source like exit 1. The deferral names the exit of the last classified failure of its deciding pass, from one table (`RECOVERY_EXITS` in `src/check-results.ts`): raise the source's `checkTimeoutMs` with `swarm_budget`; repair the host condition the output reports; or provide what the command needs (the reason names the dependency directories the checkout received), each followed by resuming the same review with `swarm_control`. The `timeout` and `unrunnable` exits also name cancelling the source with `swarm_cancel` and repairing it with `swarm_propose` (`replaces`, corrected `checks`, `maxRecoveryAttempts`, `checkTimeoutMs`) when a command is wrong. The review stays blocked until the owner acts, and each resume that meets the same failure defers again, so an `infrastructure` failure actually caused by the artifact or its check (outside the two cases kept off that path) reads as a host problem every time; there the owner's exit is to cancel or replace the source. A 126/127 row an earlier build stored as `infrastructure` keeps the infrastructure exit.
- `task/check-envelope` compares the delivered envelope with the host check rows only; the reviewer's own run is not recorded. From round 21 on, `selfRun`/`selfRunSource` describe the host check environment (older rows: the reviewer's run). A task without declared checks cannot be refused with `check_environment_mismatch`. The envelope delivered with the attempt is the only comparison basis: an attempt assigned while the adapter reported no envelope has nothing to compare, so its verdict rests on its host checks alone, whatever the adapter reports when it verifies (that report is only recorded).

## Workspace capture, outputs and preservation

- **Nothing is inferred from task text.** An ignored file is captured only as a declared output (`outputs`) or a listed `swarm_submit`/`swarm_verify` `deliverables` entry; any other ignored file, secrets included, is never swept into a snapshot. A path the prose names outside the task scope surfaces only when the submission is refused. A read-only audit task still needs its report path in `scope` and `outputs` (`[output_outside_scope]`); `[]` marks analysis-only work.
- A declared output only has to exist: `[output_missing]` checks for a regular file at submission, not that the task changed it, so a file already in the base passes unchanged and is listed in `artifact.files`.
- Rows written before round 24: a task stored without `outputs` reads as `[]` and captures and preserves no ignored file; accepted artifacts still listing `uncapturedPaths` are not named in the completion notice.
- Case-folding filesystems: a tracked file written under an out-of-scope case of the scope directory (`Reports/x.md` with scope `reports/`) is carried by the handoff snapshot, and renaming the directory cannot remove the index entry, so the replacement stays wedged. Declared outputs differing only in case resolve to one file; one written in a different case whose stored spelling is in scope is captured under the stored spelling.
- A repair that omits `outputs` and narrows scope past an inherited output gets the generic `[output_outside_scope]` exit. The draft editor has no control that declares `[]` on an untouched task; the owner edits the field and clears it.
- An untracked dependency link or directory a member creates to run checks (any `verificationDependencyDirs` name, by ancestor component) is toolchain state: it does not block preparation, and capture excludes and unstages it. A path tracked in HEAD is always work, and a regular file that merely shares a dependency name is uncommitted work that blocks preparation. The workspace-escape guard resolves the whole link chain against the committed tree, at capture and before delivery's first write.
- Switching a worktree to another task needs a confirmed stop and a preserved recovery checkpoint when it holds real uncommitted work. An unlisted ignored file the target tree would overwrite stops the switch with `[workspace_ignored_collision]` (up to eight paths named); it is not captured.
- **Inherited preservation snapshots.** After a failed preparation the replacement starts from a preservation snapshot of the previous owner's worktree and inherits every uncaptured change, including out-of-scope edits it must revert or move before `swarm_submit`. When preservation itself fails, it starts from the last checkpoint or the task base, the uncaptured work stays only in the previous owner's worktree until that member is next prepared, and `task/recovery-fallback` records `preserved: false`. A genuinely repeated failure still consumes recovery credit until the attempt limit.
- After each dependency merge the host compares every path the dependency commit changed with the composed tree (`Workspaces.droppedDependencyPaths`) and records a missing one as an integration conflict. The merge-driver case could not be reproduced on git 2.50.1, so this is verified against a tree that keeps the wrong side, not through a driver end to end.

## Review independence, pairing and rework

- **Host-added reviews.** A deliverable the plan does not pair gets one unassigned independent review at launch, at draft save and when a draft saved by an older build is listed; added reviews count against `maxTasks`. An added review copies no criteria: it checks what its deliverable must satisfy, and an override's `acceptance` adds review-only criteria. Omitted `review` override fields default to unassigned, the host's review objective, no extra criteria, the deliverable's `maxRecoveryAttempts`, and the default `maxSteps`. A review is a live review path only while a non-stopped member may own it independently (`src/assignment.ts`), so a plan whose only live members authored a deliverable wakes the owner with `[review_path_missing]` after submission.
- A submitted artifact with no live review is recorded (`task/review-missing`) after the review grace (one tick, at least 1 s); when the board would otherwise stall, the runtime admits one automatic review (two recovery attempts, a copy of the source checks). Otherwise (no eligible independent member, the task budget exhausted, a withdrawn automatic review, the automatic review of this need no longer able to reach a verdict (blocked at its recovery limit, for example: the host admits one per need), the automatic review's admission refused for this need (a copied check that now needs the host, for example: the host proposes it once per need; a busy writer or any other failure is not a refusal, and the next pass proposes again), a review deferred on the artifact, or other work still running) the submission is not reviewed and the owner is woken once per cause with the task id and reason, which names the exit that removes that cause (`reviewPathBlocker`, src/board.ts; the template adds nothing); an exit that admits a task names every allocation a launched mission's admission requires (`maxRecoveryAttempts`, and `checkTimeoutMs` for a repair with checks), which a `swarm_create` mission accepts too. Every scheduling pass derives the current cause, judging the stall once and each source after the pass's earlier admissions (two sources sharing the last task slot get one review and one budget decision; two with a free slot each both get a review), so an exit that uncovers a further cause is followed by that cause's decision; the classifier names, by that admission's own blocker rule, only what the admission does not reach: while a wedged pass keeps that admission from running, a need it has already recorded, never one still ripening towards it, and only by a blocker that holds (a recorded need the host will give a review at its next pass gets no decision); a need that ripens during a wedge is named by the wedge's own notice until the next pass admits its review or names its blocker. An unreviewable submission holds the board only while the host can still advance it, by the admission's own rule: inside its review grace and, for one the admission speaks for, while the admission names no blocker under the board's own stall (`reviewPathBlocker`; the next pass on a stalled board admits its review), whether or not the admission has recorded the need. The stall predicate and the waiting classifier read this one rule (`awaitsReviewAdmission`), so no W3 stall or fall-through names a need the next pass will satisfy by admitting a review, off-pass or wedged, also once the admission deferred that review while other work ran and that work has ended; such a board is a stall candidate, named by nothing before the admission acts. Every other stuck task is named meanwhile, and a source with a blocker is stuck work from the end of its grace, before the admission names that blocker: the W3 stall on a board with no live work, beside the review-blocked decision; beside live work its blocker is the running board, so the fall-through names the source and the other stuck work, beside the admission's deferral (wordings of one condition, the open item R20). A withdrawn review that changes the W3 stall's stuck work tells a second W3 stall (likewise R20). Both paths emit through the one review-blocked emitter: one decision per source, review need and reason, outstanding while its reason is still the blocker the runtime derives for that source under that need (it records each derived cause, even when its decision is not repeated, and derives a refused admission from that record), so a removed cause is not reminded once a pass derives the next; a cause the owner removes retires its decision at once, and the next pass admits the review. A refused admission is its need's cause, beside running work too, while it is the newest cause recorded since the need opened; a cause named before it (an exhausted task budget, no independent member, a deferred verdict) that is recorded later displaces it, and once the owner removes that cause the host proposes its review once more: refused for the same reason, it is recorded again with no second decision. Each of these facts (the grace, the record, the automatic review, the owner's decision per reason and an owner withdrawal) is kept once per review need (`reviewNeed`, src/board.ts): the submission plus each review of it that a challenge took away (the review that accepted the source, or one running or blocked). A challenge that re-opens a source this way opens a fresh need with its own grace, record, automatic review and decisions; a challenge that takes no review away (of an unreviewed submission, or one whose review is still pending) leaves the need as it was. Residual: a review of an accepted source that a challenge of the review's own prerequisite cancelled counts, once the source itself is challenged, as the re-opening of its need, dated at that earlier challenge, so that need has no admission grace (it still gets its own automatic review). A submission an older build left without an artifact is not the admission's: the host reviews only a captured artifact, so it is ordinary stuck work, named once its grace ends by the W3 stall on a board with nothing else to do and by the fall-through beside running work. Three exits those decisions name do not work for it: amending its dependencies or assignee with `swarm_control` is refused (`[artifact_policy_immutable]`: a submission's are fixed) and so is a repair with `replaces`, while it stays submitted, and a review of it is admitted but never reaches a verdict (`swarm_verify` needs the captured artifact). Withdraw it with `swarm_cancel`, which both decisions name; its repair is then admitted. A source still blocked across an upgrade from a build that keyed that decision per source (before `dff54b2`), or whose blocker reasons named no exit of their own (before batch 10), is told once more.
- **Withdrawing a review.** Cancelling the automatic review live for the current review need (admitted or re-opened for it) is a withdrawal: no review is admitted and the owner gets the `review_path_missing` "was withdrawn" decision, after any exhausted task budget or missing independent member, the causes its own exit (admit a review with `swarm_propose`) depends on. Cancelling a re-opened owner- or member-proposed review is not: after the grace the host admits one automatic review.
- **Rework in place.** `swarm_control` `action: "resume"` re-opens only a task whose own review rejected its exact commit, when it is not an experiment and no stop is pending; a budget-only amendment never reworks, and re-opens are bounded by `maxRework` (default 2). The rejecting review is re-pended with the same reviewer, archiving its verdict, review artifact, claims and `spent` into `rejections[]`, and other open reviews of the source are retired. A rejected experiment, or a dependent whose submitted work a challenged prerequisite invalidated (`task_needs_replacement`), still needs a replacement.
- **Budget asymmetry.** The source's `usedSteps` and `recoveryCount` accumulate across rounds, so a resume can be refused with `task_budget_exhausted` until the owner raises the allowance, while the re-opened review starts each round at zero. Budget warnings are keyed on task, dimension and limit, so a review that crossed a threshold while rejecting is not warned at that threshold again.
- **Same-commit resubmission.** `swarm_submit` refuses a no-edit capture of the rejected commit with `[rework_unchanged]` unless the round has a live claim. An evidence-only rework (every research rework, or an author disputing a rejection with host-backed evidence) is re-reviewed and recorded as `repeatsRejection` on `task/submitted` and `repeatsRejectedCommit` in the registry, so the re-opened review can hold a refuted and a verified verdict for one commit.
- **Evidence status is single-valued** (`EvidenceStatus` in `src/types.ts`). A verified claim that is later refuted (a challenge followed by a rejecting review, or a superseding claim that is accepted) keeps only `refuted`, so its row no longer shows that it was once verified; only the earlier `evidence/verified` event does. A claim already refuted stays refuted: a later accepting verdict neither verifies it again nor records a second refutation, and a superseding acceptance only adds `refutedBy`.
- The bound reviewer never authors the rework. If it is the only live member left, the source is listed as unschedulable in the owner's stall decision until the owner adds a member or reassigns the review; the stall text does not name that cause.
- `swarm_registry` over-reports one refutation: a review deferred, resumed by the owner and then blocked for an unrelated reason keeps its `reviewedCommit`, so the cross-mission registry reads it as refuted.

## Lineage and repairs

- One obligation has one live carrier: `[task_replaced]` refuses resuming or amending a task while any replacement of it is not cancelled, `[replacement_already_live]` refuses a repair whose target is live again or accepted, and a restart keeps a replaced row blocked. A fork through a withdrawn repair can still admit a second live carrier of the same ancestor; accepting one branch leaves the other live, named only in `task/superseded` (`liveReplacements`), with no owner notice. An older store's duplicate carrier that is later rejected gets a notice offering a resume `[task_replaced]` refuses; `swarm_cancel` is the working exit.
- Criteria are cited by position: a deliverable's `covers` names `c1`, `c2`, … and completion counts only those ids, so a deliverable whose criteria were copied as text covers nothing, and `covers` cannot be amended once a task is admitted. Before a mission exists only the draft editor re-points `covers` when a criterion is removed: a `swarm_stage` plan, an update-draft request or an automatic retry that deletes or reorders a middle criterion silently re-points every later id. Only an automatic launch refuses a criterion no deliverable cites; a draft launched from the editor or from `swarm_stage` runs, and completion then names the uncited criterion, whose exit is a new deliverable that cites it.
- A repair cannot withdraw an inherited criterion: every criterion the replaced task answers for, its own and the ones it covers, applies to its repair through the replacement lineage, which stores only its own. The mission's criteria are fixed once it exists; to drop a mistaken criterion of the task's own, withdraw the task with `swarm_cancel`, propose new work that does not name it in `replaces` and cites in `covers` the mission criteria it covered, and amend the `dependencies` of its unsubmitted dependents to name the new task.
- The owner reads stored rows only, never a derived checklist: a repair that states nothing of its own reads as `acceptance: []` with `replaces`, and a review as its review-only criteria with `reviewOf`. What such a task's worker checks is the `covers` and `acceptance` of the tasks it names, which the owner reads by `taskId`, with each id resolved by the criteria of a fresh `swarm_observe` overview; a registry row carries the mission's list as `missionAcceptance`.
- The admission guard for assumed prior work (`[dependency_assumption_missing]`) reads only a proposal's own `objective` and `acceptance`. A mission criterion the task cites in `covers`, or a criterion a repair inherits from the task it replaces, is not read, so a repair that drops its original's dependency while inheriting a criterion that assumes that work is admitted; its worker still reads the criterion in its checklist.
- Cancelled and withdrawn task rows (and host-added reviews) count toward `maxTasks`, so a repair plan that would exceed the ceiling is refused at launch; raise the mission's plan budget rather than expecting `swarm_budget` to make room.
- A cancellation's `strandedDependents` names every pending dependent that references the cancelled task and has any unsatisfied dependency, including one whose reference already resolves to a live replacement and that waits only on another prerequisite (R17-G14). The cancellation sends no notice of its own: the board classifier names each dependent no live path advances (the fall-through beside running or dispatchable work, isolation-refused work and ready work behind a busy handle included; the W3 stall on a board with nothing else to do).
- Dispatch does not re-read task prose. In a store written by `d81a3fb` or earlier where the owner amended a prose-assuming task's dependencies to `[]`, that task dispatches from the bare mission baseline; the cost is one attempt the independent review rejects, not a safety property (none of the 1,029 task rows in 17 profile stores checked on 2026-09-24 is affected).

## Scheduling passes, leases and liveness

- **A wedged scheduling pass holds its mission until its await returns.** The watchdog names it past `stallPassTimeoutMs` (default 30 × `tickMs`), once per naming fact (the mission's unfinished work at its epochs, which includes the live work that held the body, and each member's counted start failures: a body that wedges on a fact the owner already holds is told by that row and its naming writes nothing, whatever the board digest is; either way the naming is a publication, so board facts committed while that body was still inside its bound are told when it is named, not when the hung call returns), but nothing releases it: lease recovery, completion and the budget check wait for the await's own bound (`workerStartTimeoutMs`, the per-attempt delivery bound, or `HOST_GIT_TIMEOUT_MS`, 5 minutes per git subprocess), and capture and preparation have no overall bound. A body stops early only when one member held it for a whole bound, so a sweep of members that each take less runs however long it takes. The notice clause "produced no durable state change" is unconditional. Another operation on that mission that waits past `stallPassTimeoutMs` is refused with `[mission_operation_pending]`. The naming stays deliverable while any task it named is unfinished at the epoch it named, whether or not a body is still past its bound and whatever became of the other tasks it named, so an owner inside a long step reads it after the body has settled and one still queued at a restart is delivered; its reminders (at most two) follow the same rule and name the work it named that is still unfinished at that epoch, whether or not a live path advances it. A body that wedges with no unfinished work names the mission root, which stays outstanding, deliverable and reminded, while the mission is unfinished: a body is named once, so work planned while it is still wedged is never named for it, and the board does not record whether it is still wedged, so the naming is also reminded after its body settled, on a board whose work runs under a live lease. A later body that wedges on a different set of unfinished work is a new naming, so a task both namings name can be reminded through each.
- **Decide-then-act is not done.** Adapter calls (start, prepare, capture, deliver) run inside the mission's serial queue; moving them out changes event ordering, which the replay digest pins.
- The default attempt lease is 120 seconds, renewed only while the adapter identifies an owned, uncancelled native operation or provider retry (a live stream republishes every `activityHeartbeatMs`, default 1000 ms), and never past the mission deadline. `activityHeartbeatMs: 0` disables that republish timer: once the runtime has cleared a member's persisted activity (a budget pause clears it), a silent operation is not published again until a model stream produces a chunk or the operation ends, so its lease is not renewed in the meantime. This is operation liveness, not useful progress: a stuck operation relies on its own timeout, cancellation or the deadline, and persisted activity never renews a lease after a restart.
- `maxIdleCloseouts` (default 2), `stallPassTimeoutMs` (default 30 × `tickMs`), `stallPassLiveGraceMs` (default: the effective `stallPassTimeoutMs`) and `attemptSilenceBoundMs` (default 600,000 ms, `0` disables) are runtime configuration the plugin `Config` schema does not declare: a profile key of that name passes through unvalidated. A `stallPasses` key is ignored: the no-progress window it set was removed, since the board classifier judges every pass end. An invalid `stallPassLiveGraceMs` or `attemptSilenceBoundMs` falls back to its default, but a `stallPassTimeoutMs` that is not a number or is below `tickMs` becomes `tickMs` (one tick, not 30 × `tickMs`), and `stallPassLiveGraceMs` then defaults to that one tick as well. `maxIdleCloseouts` is used as given.
- No judgement of a board is skipped: every pass end and every publication outside a live pass runs the board classifier (a publication during a live pass is that pass's to judge at its end), and each family tells only its own fact, deduplicated on the deliveries ledger, so a stop bound, lease end, review grace or preparation back-off that expires with no durable write is judged at the next pass end (the tick kicks a pass for every non-terminal mission). Residual: an expiry while a scheduling body is held inside its bound is judged when that body settles, at the next transition after it, or when the watchdog names the body; the board's stall predicate (`stalled`, src/board.ts) reports a board whose only work is in back-off as a W3 stall; and a pass that blocks the mission on its budget or deadline ends before its judgement, so the budget terminal speaks alone and the board's W3 stall is told once the owner resumes the mission.
- The no-silent-state backstop witnesses a dispatchable-but-undispatched task only when an eligible member is startable (parked, or idle by the adapter's contract); a board whose eligible members are all busy is not silent. The dispatch question is one namer among the board's: the board's own fact (the W3 stall, or coverage-complete) and the fall-through are judged beside it, and the fall-through leaves the dispatchable work to the question.
- A task whose every capable member was retired for start failures (three consecutive failures reroute a member's work) stays pending. The retirement notice names it with each retired member's failures and last error, and the board names it too (the dispatch question while a capable member could still be started, then the W3 stall when nothing else runs or the fall-through beside running work): wordings of one condition (the open item R20 under owner notices). All stay outstanding, and only the retirement notice names `swarm_add_member`, the exit that lets unpinned work run when no live member could. In an all-routes-fail storm the start failures and the dispatch question spend the owner's wake window, so the retirement notice can ride the wake-budget summary, which truncates each fact: the summary names the task and points to `swarm_observe` with its `deliveryId`, and the `swarm_add_member` exit is reached through that call, which returns the fact in full. Provider-outage start pacing is in process memory: after a restart a member inside a recorded outage window is probed once immediately, then once per window, and work preferring it waits up to one 5-minute window unless the owner amends `assigneeId`. Only a start that opens a member's session records its route as recovered (`provider/recovered`) and clears its recorded outage; a scheduling pass that finds the worker running adopts it and records nothing. An outage the adapter reports during a running turn therefore stays recorded on the member until its session is next opened, and the in-place retry that succeeds records no recovery. The route is quiescent only for one window after the outage's last report (`providerQuiescent`, src/types.ts): start pacing, re-routing and the live-work panel's "Waiting for provider recovery" all read that one window at the live clock, so a member whose in-place retry succeeded shows that state, its activity hidden and not counted as working, until the window ends.
- A stop whose recorded owner has no member row is refused as unconfirmable (`mission/stalled`, cause `worker-stop-failed`, `deterministic: true`) and its task stays fenced. Only a corrupted or hand-edited row reaches this (members are never deleted); a `swarm_control` resume repeats the refusal, and the exit is `swarm_cancel` plus a repair via `swarm_propose` with `replaces`.

## Owner notices and wakes

- Owner notices cover decisions, blockers, failures, budgets, stalls and exceptions (a parked holder, an integration gap, provider outages, a rendezvous, a deferred verification, a challenge, a recovery fallback, a duplicate carrier, typed escalations) and completion. Submission and acceptance appear only in the panel and event log; routine progress must be observed explicitly.
- A proposal refused at a mission admission limit (`maxTasks`, `maxExperiments`) is one `[task_ceiling_terminal]` request per limit, whoever proposed it (`SwarmRuntime.propose`, `src/runtime.ts`): a refusal under a limit the owner already holds, the owner's own or any worker's, is only its tool error, and a refusal under a raised limit is a new request. Each worker refusal records a `task/proposal-refused` event naming the proposer; the request names the mission root, not who was refused, so a second worker refused under the same limit wakes no one and is read in the event log. The request's exit is `swarm_budget` with a raised `budget`, after which the refused proposer retries its own admission; the raised limit answers the request, which is neither delivered nor reminded once the limit it met is no longer the mission's. A refusal an older build recorded under the proposer's key (`task/proposal-refused:` or `budget:`) matches none of these, so a limit refused again after the upgrade is announced once more.
- A guard-chain terminal (`[budget_terminal]`, `[workspace_terminal]`, `[attempt_terminal]`, `[task_ceiling_terminal]`) is one decision per chain and the fact that opened it: a limit value, a budget pause, a task at its epoch, an attempt, a member's unfinished work at its epochs with the text of its dispatch failure, an isolation violation. The same opener is never announced again, whatever the board looks like (a proposal refused again under the same limit, by any proposer, is only the tool error); while the work it names is unresolved, its row's reminders (at most two) carry it. A member whose dispatch fails with the same text over other work (a later task, a new epoch, one more task) is announced again, naming that work; one that still fails after its work was withdrawn or reassigned holds none, which is announced once per failure text, naming the mission root, although the request's wording still says "the held work". A dispatch failure whose text differs on every pass wakes once per distinct text, bounded by the wake budget. That terminal and the dispatch question are two wordings of one condition (the open item R20): when a member's dispatch keeps failing, the pending task its terminal names is also asked about once, at that task's epoch, in the question's own wording. The question reads only what a pass tests (readiness, the start blocker) and its own rows on the ledger, and has no predicate that says a member's dispatch chain is failing. A terminal an older build recorded under a board digest matches none of these keys, so a condition that fires again after the upgrade is announced once more. An `[attempt_terminal]` names its chain's exits whatever opened it. For an abandoned close-out or a failed lease-expiry checkpoint the recovery that raised the request has already re-pended the task, usually running again under a new attempt by the time the owner reads it: `action: resume` is accepted and leaves that attempt running, and `action: amend` with `changes.assigneeId` fences it for the named member. For an exhausted recovery (the task blocked at its recovery limit) both are refused: `swarm_control` with `action: amend` and `changes.assigneeId`, and with `action: resume`, each return `task_recovery_exhausted` ("Raise maxRecoveryAttempts before resuming exhausted automatic recovery") and change nothing. The exit that works is the one that refusal names and the request does not: `swarm_control` with `action: amend` and `changes.maxRecoveryAttempts` above the attempts spent, which resumes the task. The wording and the refusal are older than the opener keys.
- `swarm_observe` and the arena view expose at most the newest 20 owner notices (`noticeLedger`); an older escalation is durable but not surfaced there.
- **Wake budget.** Each mission's owner gets at most 6 individual notices per 5-second window (`DEFAULT_WAKE_BUDGET`, `DEFAULT_WAKE_WINDOW_MS`); further facts ride one summary per window that lists every fact, so it bounds bursts, not a lifetime. The window is in process memory, so a restart opens a fresh one. A rendered fact list is bounded at 3,200 characters (or `maxMessageChars`, if smaller), each fact compacted to 440; full facts stay on the durable delivery (`swarm_observe` with `deliveryId`).
- Fact identity is keyed on the event type: a second distinct same-type transition at the same subject@epoch with the same recorded reason is suppressed, and a reviewed template's family replaces the trigger (both at `factKey` in `src/notices.ts`). Every notice names its fact: `NotifyOptions` requires a trigger or an explicit key, so no row is keyed by its class alone. A site whose transitions recur at one subject@epoch records the opener that tells them apart in its reason: a start failure below the retirement bound and a challenge are each opened by their own event (`member/resume-failed`, `evidence/challenged`), so failure 2 after failure 1 and a second challenge of one claim are each told; a preparation failure and a deferred verification are keyed by their recorded reason. A member failure is the member on its open work (the mission root when it holds none), like the outage below: the provider's text, which can carry per-request data such as a requested token count, is the body and never the identity, so a member whose requests keep failing on the same work is told once, whatever each error says, and its row's reminders carry it; another member, or the same member over new work, is told. A provider outage is its class on the member's open work (the mission root when it owns none): another class is told, while a retry (with or without scheduling passes between reports) and a return to a class already told on that work are that fact again, carried by its row; the same class over new work is told. A member with no open work is therefore told each class once while it holds none. The adapter reports a classified provider error as that outage alone, never also as the member's failure, and the 30-second window that bounds the `provider/outage` event to one per member and class does not gate the notice. A generic decision an older build wrote (trigger `decision`, key `decision:<mission>:<subjects>:none`) is an unclassified legacy fact: it stays deliverable whatever its subjects' state, since no relevance rule reads a class-named trigger (the rule that withheld one whose submitted subjects had gained a live review is deleted), and the same facts fired again after the upgrade are told once more under their own keys.
- **Change and return.** No notice identity contains the board digest, a wall clock or an in-memory counter: a key is the family, its scope and the durable fact that opened it. A condition that ends and returns with the same opener (the same stuck work at the same epochs and reason, the same review need and blocker, the same isolation violation) is the same obligation: its row is outstanding again and only its remaining reminders (at most two over its life) speak. A return with a new opener (an epoch, a review need, a limit, a budget pause, a counted start failure, a violation text) is a new fact and wakes the owner.
- **Upgrade from a build before batch 11.** Rows whose key is unchanged keep deduplicating: stall roots, review-blocked decisions, dispatch questions, parked holders, fall-throughs, integration gaps, absence reports, reminders, owner-reply nudges, silence escalations, worker delivery failures, budget reviews (so no budget threshold is warned again), wedge namings, and guard terminals keyed by a question, a stop, a workspace revocation or a pending mission operation. Every other condition that is open at the upgrade, or fires again, is announced once more under its new key: the W3 stall (`board-stall:`, formerly `mission/stalled:`, whose old row may still send its unspent reminders), coverage-complete (`coverage-complete:`, formerly `task/accepted:`), a guard terminal an older build keyed by the board digest, and the formerly generic facts above. The first publication after the upgrade runs every classifier, so a decision an older build's board witness had suppressed (a fall-through, a dispatch question, an expired stop, lease or review grace) is told once. Fields older builds wrote on a mission row (`witness`, `stallNotice`, `coverageNotice`, `schedulingStallNotice`, `schedulingWedgeNotice`, `budgetWarned`, `isolationRefusal`) are inert: nothing reads them, and that mission's snapshot still shows them. An old `mission/stalled` event keeps its unread `ownerNotified` field.
- `tests/r17-notices.test.mjs` rebuilds reviewed bodies from durable rows with the production template (`renderNotice`), checks their stated counts and keeps tool/exit anchors for seven of the eight `NOTICE_TEMPLATES` families (`duplicate-carrier` is rebuilt in `tests/lineage-retirement.test.mjs` without anchors). Because the rebuild calls the production template, a template edit that adds a claim outside those counts and anchors is not caught. The other `notify(` sites are enumerated per site and are not replayable from one template.
- Cause-bearing notices are transition-driven. The sampled tick (`sweepDecisions`) emits exactly two absence instruments and no cause: the absence net (default 600,000 ms, `Notices.absenceBoundMs`, measured from the mission's newest progress-kind event anywhere in the append-only log, or its `createdAt` before one: `EventSpec.progress` in `src/events.ts` declares the kinds and `SwarmStore.progressAt` reads them, never through the bounded `maxEvents` window, so telemetry, transport and scheduling rows such as `member/activity`, `trace/span`, `message/queued` and `mission/pause` never move it) and the attempt-silence escalation (`Scheduling.sweepSilentAttempts`, `attemptSilenceBoundMs`), which state silence and elapsed time, not a cause.
- The false-wake rule is judged only at delivery: `ownerDeliveryRelevant` withholds a notice whose subject a live lineage covers, at delivery and at native consumption, never at emission; the withheld row stays durable and is delivered once its lineage closes.
- A rejected stall root that strands nothing beyond its rejecting review is never sent: it is recorded against the rejection decision's row (`coveredBy`), whose reminders carry it, unless that decision rode a wake-budget summary, in which case the root is its own fact. A rejecting review is cancelled only when its repair is accepted and is not named on its own before then.
- **Every board-level naming is told while its condition holds; one wording per condition (R20) is open.** The board's own namings (a stall root, the W3 stall, the dispatch question, the fall-through) are each told whenever their own condition holds, whatever owner decision already names the same work. The only older rule that removes one is the covered stall root above: a stall root at the same subject@epoch as the verify site's rejection decision, when it strands nothing beyond its rejecting reviews. An owner decision's openness governs only its own delivery and reminders. The dispatch question asks about the first ready task that did not dispatch and is not yet asked about at its epoch, so successive judgements reach every such task, once each. The same stuck task can therefore be named twice or more in different wordings: a failed dispatch's `[attempt_terminal]` or an isolation request beside the dispatch question; a start failure or a retirement beside the dispatch question and the W3 stall or the fall-through; a workspace revocation beside a stall root and the W3 stall; a ceiling or recovery request beside the stall root of the task it blocked (`tests/faults/f19-no-silent-state.mjs` row 7c); a review-blocked decision beside the W3 stall (beside running work, the fall-through); a second W3 stall after a withdrawn review changes its stuck work, and likewise a second fall-through when its stuck set grows; and, while a scheduling pass is wedged, the dispatch question about each task the wedged sweep has not reached, beside the wedge's own naming. Each extra wording spends a slot of the owner's wake window, so in a burst (a start-failure storm) a later fact can ride the window's summary: the summary names each task and points to `swarm_observe` with its `deliveryId`, which returns the fact in full on its durable delivery, exits included. Batch 11 tried twice to let one record stand down for another that names the same work and withdrew both: B1 (a board naming deferred to an open decision) and D1 (an unreviewable submission's decision spoke for the whole board); each left a stuck task with no notice. One wording per condition needs every decision's openness bound to its cause first. The decide-then-act Notices slice (S12) made the families judged by the subjects they name (a stall root, a review blocker, a parked holder, a dispatch question, a wedged pass's naming, a fall-through) each one rule that their delivery and their reminders read (`Notices.outstanding`), and left R20 open: most guard-chain requests (a recovery limit, a ceiling, a close-out failure, an abandoned close-out, a failed checkpoint, a revocation, a failed dispatch) and the other decisions that name a task (a preparation failure, a rejection, a member failure) are still outstanding by their subjects' state, not by their cause, and a member-scoped request names the member's work, so a board naming deferred to one could fall silent.
- Delivery, consumption and resolution are three facts. Transport state (`sent`/`queued`/`claimed`) is derived from `deliveredAt` and never asserts consumption; consumption is the delivery's own `consumedAt`, one field for an owner notice and an owner question alike, recorded once from the host's inbound `user/message` into the owner session after native pre-step admission. Its one writer is `Notices.recordConsumption`, and the one observer of that message is the owner-reply guard's host subscription. The guard first books the turn's open questions, each one the transport delivered, an earlier admission consumed or this message admits, and then records the consumption. The observer is best-effort: a consumption write that fails is dropped and that delivery stays unconsumed (a miss reported for it states `consumedAt: null`), while the turn keeps every question it booked. No host signal shows a notice was acted on, so "handled" is untestable; resolutions are task or mission transitions. `NoticeEnvelope.claimedAt` (`src/types.ts`) is dead, declared only for rows older builds wrote.
- Outbox failures keep their message identity and a durable diagnostic, but there is no per-route failure counter or backoff policy, and offline-owner notifications can remain pending. Each delivery attempt is bounded by `stallPassTimeoutMs`; one the adapter never settles is abandoned, recorded (`outboxStarved`) and retried by a later pump, so adapter acceptance must be idempotent.
- `completeAutomatic` commits the completion and its `automatic/completed` event plus owner notice in two transactions; a crash between them loses the notice.
- An owner-assembled mission (no saved start request) never completes automatically: at full coverage it sends one coverage-complete decision per coverage state (its terminal tasks at their epochs), reminds the owner of it at most twice, and stays active until the owner completes it.

## Refusals and diagnostics

- Only a `PolicyError` (or subclass) reaches the browser with its message and code; outside the two validators below, every plain `Error`, even one carrying a `[code]`, arrives as `internal-error` ("Swarm request failed unexpectedly"). `src/` has 284 `throw new Error(` sites at `73cf4fb` (`git grep -o 'throw new Error(' -- src | wc -l` counts the current tree). Many are invariant, corruption and argument guards, but some are refusals a caller can trigger, and a browser action that meets one sees only `internal-error`: `controlStart`'s refusals of an automatic request's `retry`, `stop` or `extend` in the wrong state (for example `This request already launched; control its missionId instead`) are plain `Error`s. `prepareTask`'s two `Dependency …` refusals are untyped; they run only in scheduled dispatch and `swarm_claim`, never under a browser RPC.
- A `PolicyError` whose text names host detail (`/Users/`, `/tmp/`, `SQLITE` and similar) or exceeds 4,000 characters also arrives as `internal-error`, except an admission refusal naming host detail, which gets a fixed repair text built from its diagnostics' codes and locations (a task-graph refusal gets one fixed `[task_graph_invalid]` text). `[check_requires_host]` quotes the classified `package.json` script body, which is owner-controlled workspace content plan validation already shows.
- **The plan and model validators echo their failures verbatim.** Plan validation (`validatePlan`, run by the `create-draft` and `update-draft` RPCs) and worker model selection (`workerModelSelection`, run by those and by the `launch-draft` and `add-member` RPCs) are wrapped as user-actionable (`exposed(…, true)` in `src/web-api.ts`), because their failures describe the caller's own input. Any non-empty failure message from them reaches the browser as `bad-request` with that text, including a plain `Error` (a cyclic plan's `Plan contains a dependency/review cycle`), a message naming a host path and one over 4,000 characters; such a failure carries no policy code. Only a `PolicyError` that passes the host-detail and length checks keeps its code. `launch-draft` re-validates the saved plan inside `runtime.launchDraft` under the ordinary boundary, so a launch-time plan refusal keeps its code only as a `PolicyError` that passes the host-detail and length checks, and otherwise arrives as a fixed repair text (an admission or task-graph refusal) or `internal-error`.
- The refusal lint (`tests/refusal-diagnostics.test.mjs`) holds only `src/tools.ts` and `src/admission.ts` to the full contract (one stable `[diagnostic_code]`, an imperative next step, parameters resolved against the schema from the real `registerTools` path), with an empty allowlist. Fourteen other files are only inventoried: at `73cf4fb` the report reads 472 sites, 415 not coded to that contract (`node --test --test-name-pattern='refusals outside this branch' tests/refusal-diagnostics.test.mjs` prints the live count). Only the literal parts of a template are checked (`partial` sites such as `[check_syntax_invalid]`, whose `/bin/sh:` diagnostic the host-path scrub hides), and `missingReviewDiagnostic`'s exit is carried by each blocker's reason (`reviewPathBlocker`, the automatic-review admission failure and the classifier's fallback): the lint holds only the exits those reasons share (`ADMIT_REVIEW`, `WITHDRAW_SOURCE`) to the call-exit contract (`CALLER_COMPOSED_MESSAGES`), and `tests/review-blocked-exits.test.mjs` performs every exit a reason names.
- `PolicyError.toString` renders like a plain `Error`, so stringified failures read `Error: …`; rows recorded before round 22 for refusals that were already typed read `PolicyError: …`.
- A refusal's trace span `error.type` is its declared category, not the text classifier's reading; the classifier remains the fallback for untyped failures.

## Resources and budgets

- The primary agent chooses and can revise budgets. Token accounting uses provider-reported worker usage, with cache-read input charged at `cacheReadWeight` (default 0.1, bounded 0..1) and warnings at each `budgetWarnAt` fraction (default 0.7 and 0.9). A step is refused when consumed usage plus an estimate for requests still streaming (each worker's average per-request usage) reaches the ceiling, so an unusually large in-flight request can still exceed it. The owner conversation's usage is attributed to its newest live mission or planning request by time window and not charged to the pool, and failed provider attempts that report no usage stay uncounted.
- A budget warning's `suggestedLimit` is a threshold-headroom floor, not an estimate of remaining work. Mission duration measures execution time excluding pauses and idle waits; an explicit `deadlineAt` stays a fixed wall-clock deadline.
- Boundary compaction: a verdict (accept or reject) requests it for the reviewer and for the reviewed author. It runs only while that member's agent is idle, and only when the member's last request carried at least `boundaryCompactionTokens` prompt tokens (default 250000; `0` disables it). An idle member compacts at the verdict. A member still in its turn keeps the request and compacts at its next idle, before input queued behind a rejected step starts the next unit. Both supported web profiles mount `compaction-basic` inside each agent preset's isolated `compaction` realm, so the adapter reaches the engine through the `/compact` command the member's own composition resolves (`commands.find`). A host-plane `compaction` service is the fallback. A composition with neither is reported once in the host log and compacts nothing. The summary request is charged to the member like any request (`compaction/summary` usage, both live and on restore), and so is the summary of the host's own pressure compaction. A session restored after upgrading charges its earlier summaries once. No remaining-budget check runs before a compaction. Remaining gaps:
  - Only a verdict requests a compaction; a handoff, cancellation or ceiling block does not.
  - When a member's driver carries straight into queued next-turn input without going idle, the compaction waits for the idle after that unit.
  - Prompt pressure is kept in process memory, so the first boundary after a host restart is skipped unless the member has made a request since.
  - A compaction the engine refuses (for example, busy while a human `/compact` runs) is logged and not retried.
  - Through `73cf4fb` the adapter looked the engine up with `ctx.get('compaction')`, which the preset realm isolates, so no boundary compaction ever ran (0 of 288 recorded boundaries over 250K).
- **The task-ceiling guarantee has a durable window and a contract window.** A handle whose task hit its own ceiling takes no further mission-charged step: the step brake enforces this from the fence until `workers.stop` confirms, for every fence cause and regardless of fresh input; after that it rests on the adapter's stop contract, not a durable row.
- A start rejection naming an unsupported `reasoningEffort` is retried once without it (`member/effort-downgraded`); the downgrade clears the effort rather than choosing a supported one, and a second rejection stops the member (`member/effort-rejected`, `member/failed`).
- `SwarmRuntime.criticalPath(missionId)` (the CRITICAL PATH metric) is accounting only; no budget enforcement reads it.

## Storage, recovery and durability

- Opening a store upgrades schema 0 to 6 to schema 7, which older builds reject; a downgrade needs a consistent pre-upgrade backup or a separate state path, with the matching workspaces, recovery journals and Git refs. A database from before round 25 keeps an unread `passes` table. The schema 4 upgrade runs once, inside the opening transaction (and on a restored older snapshot): a staged mission takes its saved draft's criteria, as that draft's relaunch would have written them, and every existing task and draft plan task keeps in its own `acceptance` only what its checklist does not already take from its review source and from the tasks it replaces (a repair drops the criteria it inherited, a review the copy of its source's list), while a deliverable cites in `covers` the ids of the mission criteria left in that list and their text leaves it. Each row is then what this version would have stored for the same proposal, which keeps every worker's checklist and each completion verdict, except that a repair admitted before acceptance inheritance now also answers for the criteria of the tasks it replaces, so such a mission can become completable and, if automatic, completes. The upgrade is one recorded state change, and a saved draft it rewrites moves to its next revision: an editor page left open across the restart reloads that draft, and one holding unsaved edits has its save refused as a revision conflict until it is reloaded. The schema 5 upgrade runs once the same way, and as one recorded state change when it rewrites a row: an owner notice's consumption, which earlier builds recorded on its notice envelope beside the signal that recorded it, moves to the delivery's `consumedAt`, and the signal is dropped. The schema 7 upgrade runs once the same way, and as one recorded state change when it rewrites a row: the markers an attempt writes while it runs (the budget pause that preserved it, its idle signal and idle close-out nudges, its denied git write and its lease warning), which earlier builds kept on the task row beside the attempt, move onto that attempt, the budget pause as its `pausedBy`, so they leave the row with it; a marker that belongs to no attempt the row holds is dropped: every marker of a row that holds no attempt, and a budget-pause or idle-signal marker naming another attempt (builds before schema 6 could leave them after a fence took the attempt and carry them into the next attempt). Events, and deliveries apart from that move, keep the shapes they were recorded in.
- Only task rows are compare-and-swap writes (`stale_task_revision`). `Mission`, `Member` and `Delivery` rows are whole-row puts, so a read-modify-write across an `await` on them can lose an update. The outbox acknowledgement and consumption re-read their rows inside their transactions; other asynchronous whole-row writers still need individual review.
- Automatic startup snapshots tracked and non-ignored untracked files without moving the branch or changing the index; ignored files (dependencies, local environment files) are left out, conflicts and dirty or diverged submodules must be resolved first, and the capture retries on concurrent edits but is not a filesystem-wide atomic snapshot.
- Worker worktrees, planning snapshots and artifact refs are retained after stop/completion, with shared Git objects and refs under `.git`; cleanup is explicit. Verification checkouts are disposable: each verification that runs declared checks removes its own checkout, and when git refuses, the host removes the tree itself, reports the refusal (`task/verification-cleanup-failed`) and tries to drop the checkout's registration in the source repository. A checkout left by a process that died between `git worktree add` and that cleanup (SIGKILL, OOM), tree and registration, is reclaimed by the next verification of the same mission that runs declared checks; a leftover of a mission that never verifies again is retained like member worktrees. The verification cleanup's reclaim acts only on entries and registrations under the mission's own `verification/` directory: it removes a link there without following it, reclaims nothing but its own checkout when that directory is not canonical, never touches a checkout another in-flight verification of this process owns, and never runs `git worktree prune` (nor does the retry after a worktree-metadata race, which for any worktree add, member worktrees and planning snapshots included, reclaims only its own target and fails the add with the reclaim's own cause when that target's tree resists). A tree that resists is never handed to git, so its registration stays until a later reclaim removes the tree. A registration whose tree is already gone is found only through `git worktree list`, so it waits for a later verification when that listing fails. A registration git left locked without a recorded path (a crash inside `git worktree add` before it wrote `gitdir`) cannot be found by path and stays until removed by hand from the source repository's `.git/worktrees`. **Apply result** updates only working files and is not a filesystem-wide atomic transaction: concurrent edits trigger rollback, later edits that prevent restoration leave identified recovery copies, and a hard process or disk failure mid-write may need them recovered by hand. Submodule changes and directory/file conversions are not applied. Snapshot storage must be outside the source repository.
- Stable IDs and a durable inbox recovery journal cover the tested stop/restart paths; they do not guarantee exactly-once external side effects or recovery from arbitrary disk faults.
- Snapshot restore records a durable restore intent and startup finishes an interrupted replacement; this covers the tested interruption points, not arbitrary filesystem corruption or a device that ignores durability requests. A full WAL/umask permission matrix has not been validated.
- Trace metrics describe the retained span window (at most 20,000 spans per mission) and its truncation, not whole-history totals; parent lookup can still read exact durable task/attempt records. The recorder keeps one index per mission for the process lifetime, so its memory grows with the missions a long-lived host traces.
- Span payloads are digest-only (digest and size of input and output). Spans cover the `swarm_*` tools, which have no `ToolRun` rows, and a planning call's input carries the host's realpath-resolved `workspace` in place of the model's value, which no session log holds, so a digest orders a step but cannot be resolved to its payload; decisions are reconstructed from events and rows. The `traceSpill*` keys are accepted and ignored.
- Span recording is best effort and never changes a tool's result: each `swarm_*` call records at most one span, carrying the command's own outcome. Only a call scoped to an existing mission is spanned; a call naming no mission or an empty or unknown one, a prelaunch `requestId` whose request has no mission yet, a `swarm_stage` call (a draft is not a mission) and a `swarm_create` call refused before its mission exists are counted per step in `unscopedSteps` (`swarm_observe` with `trace: true`; process memory, so a restart resets it). A span whose scope read, build or write fails is contained: the tool still returns the command's own result or error and no span is written. That failure is only counted, in the in-process `HostTelemetryLink.counts().failed` instrument together with host-sink failures; no tool, notice or panel reads it and the error itself is not kept, so the retained window can miss a step. A stored span row with a malformed id is never used as a parent (the next span is a root) but stays in the metrics window and counts as a contract violation. A span's end time is its start time plus a monotonic duration, so a wall-clock step cannot reorder it.
- **Member phase vs. derived status.** Only the member `phase` (`active`/`parked`/`stopped`) is persisted; `status` is derived on every read. Legacy rows without a phase are mapped by `src/projection.ts#memberPhaseOf` (`stopped` stays stopped, `waiting` becomes parked, `idle` and `working` become `active`), so a legacy `working` row that owns no running attempt now reads `idle`. Such rows keep their old `status` until their next write; no migration runs at open and none is recorded.

## Interface and observation

- The live sidebar observes committed changes through native RPC long polling with bounded change history. Updates carry changed mission snapshots, not individual tokens, and no completion time is guaranteed; a busy host, browser or network can delay delivery, so this is not real-time. A disconnected panel marks its activity stale until it refetches. Conversation cards are historical snapshots; an explicit observation makes a new one.
- `watch` long polling returns on any commit in a visible scope, and a live model stream commits its member row at each `activityHeartbeatMs` republish, so a panel watching a busy mission wakes about once per second.
- The browser RPC derives its actor from the client-supplied `sessionId`; there is no plugin-side session binding (single-user profiles mitigate it).
- Cold worker history is a read-only text/tool projection, not the native chat UI: media is represented by type and long entries are truncated. A live worker's native composer may remain writable; mission-management permissions are checked separately.
- Observation output is focused and paged but has no fixed byte limit: a task with very long acceptance or objective text is returned whole up to the excerpt limits.
- The mission board (`swarm_post`, `swarm_board`) is an append-only channel of six closed kinds (`ASK`, `ANSWER`, `IDEA`, `ALERT`, `ARTIFACT`, `HANDOFF`) whose sequence is global across the missions in one store (A2-07), not a per-mission ordinal; read state is client-side. A post is data, never authority: it changes no task state, queues no delivery, writes no file and emits no event row.
- **The client panel is a projection of a bounded event window, and the board is model-tool-only.** `tests/client-findings.test.mjs` (F-14/F-33) fails unless every emitted event type is labeled by the compact projection or named in an omission list with a reason; `task/check-envelope` and the install-scoped `store/*` rows are omitted. `swarm_board` and `swarm_observe` return posts and the caller's inbox to a model session, but the client `Snapshot` carries no `posts`/`inbox` field and the panel renders no board posts; a browser board would need its own per-mission projection and read cursor (a projection gap, not an authorization boundary). `workspace/grant-loaded` is install-scoped (`swarm/install`) and never in a mission snapshot, while `mission/workspace-bound` and `mission/workspace-revoked` render in the compact panel and Activity view (after a fence, the owner facts it opens are newer than the revocation, so the compact panel's three events are theirs).
- The Activity view groups the bounded snapshot window (`snapshot.events`), so a group's count is of retained events, not the whole log.

- **The runtime clock is for tests.** The plugin always runs on `Date.now` and ignores profile keys `now` and `manualTick`. ## Code structure

What remains of the structural debt the 2026-09-24 review named (M-10):

- **The runtime is one large class.** `src/runtime.ts` is one `SwarmRuntime` class of about 3,900 lines: it implements the kernel every seam stands on (`src/kernel.ts`) and still holds the tool, control, planning, admission and recovery paths itself. The seven seams it builds no longer hold it: each is constructed from the kernel and the seams below it, in the order refusals, notices, attempts, workspace admission, declared checks, gates, scheduling, and none imports `src/runtime.ts`, even for a type: counting type-only imports, the src import graph has no cycle (`tests/import-cycles.test.mjs`). Two reaches above the kernel remain: the scheduling seam also takes the runtime's worker start and task assignment, and the notices read the scheduling pass state through a closure the runtime hands them.
- **Other large modules are not split.** `src/workspaces.ts` is one class for worktrees, baseline checkouts, task preparation, capture and verification; `src/notices.ts`, `src/types.ts` and `src/tools.ts` are single modules. Prefix-scope matching is still written twice, as `scopeKeysOverlap` (`src/scheduler.ts`) and `withinScope` (`src/scope.ts`).
