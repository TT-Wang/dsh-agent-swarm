# Agent Swarm for DeepSeek Harness

[English](README.md) · **简体中文**

### 一个目标，一支协作团队，一份可审查的成果。

描述你想构建的功能、修复的问题或调查的方向。Agent Swarm 将一支协作团队带入 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)：成员围绕共同目标工作，执行过程清晰可见，成果经过独立复核，再由你决定如何带回项目。

```text
/agent-swarm 修复搜索结果重复的问题。保留现有 API，补充回归测试，并独立验证修改。
```

主 agent 理解项目、组织工作，并根据任务决定成员和资源预算。你可以在侧栏跟进任务，在成果就绪后查看修改。

**v0.7.0 · MIT 开源 · 本地 Git 项目 · 原生集成 Harness**

[开始使用](#get-started) · [查看界面](#ui-gallery) · [了解架构](#architecture) · [English](README.md)

## 适合交给团队的工作

| 你的目标 | 团队如何协作 |
| --- | --- |
| 修复难以定位的问题 | 调查原因、实现修复，再由其他成员检查边界情况。 |
| 完成横跨多个模块的功能 | 拆分可以并行的工作，协调依赖，整合经过复核的成果。 |
| 理解陌生代码 | 收集证据、对照不同发现，并按要求提供不修改代码的分析。 |

**你描述结果，主 agent 组织协作。** 每次启动无需填写成员人数或 token 预算。成员可以在任务范围内交换发现、相互询问、质疑证据，并交接阶段成果。

## 从一句需求，到项目中的改进

1. **从项目现状出发。** 规划前先创建私有 Git 快照，包含已跟踪文件的改动和未被忽略的新文件。无需手动 commit，快照过程保留你的分支、暂存区和工作文件。
2. **让成员协同推进。** 主 agent 按可独立验收的结果和真实前置条件拆解工作。偏好成员忙碌时，满足执行条件的空闲成员可以接取尚未开始的待办；明确绑定和在途任务仍受保护。成员使用原生 Harness 会话与独立 Git worktree。
3. **复核实际提交的成果。** 由其他成员审查提交内容。对于代码任务，Harness 还会在准确的提交版本上执行声明的检查。
4. **就绪后再带回项目。** 任务完成后，侧栏为最终已验收的代码成果提供“查看修改”和“应用结果”。应用以初始快照为基准，保留你的分支和暂存区，不会自动暂存、提交或推送。

你原有的编辑属于任务基线，不会被算成 swarm 新增成果。检测到合并冲突时，会先报告，再由你处理。

## 随时知道任务在做什么

侧栏回答三个实际问题：**谁在工作？刚刚发生了什么？哪里需要处理？**

- **认得出每个成员。** 宿主持久分配名字，职责单独展示，仍支持明确自定义名字；稳定的机器人头像不会因改名或职责调整而改变；打开成员会话即可查看具体工作。
- **看得见当前执行。** 展示正在进行的操作、持续时间，以及 Harness 最近一次观察到活动的时间。新鲜的活动信号驱动动画；信号过期后显示为待确认。
- **用事件呈现进展。** 工具结果、提交和验收进入活动流。资源用量保留在详情里，不会被当作完成百分比。
- **操作就在手边。** 在侧栏暂停、继续或停止任务；启动失败时，也能对已保存的规划请求执行恢复操作。

界面跟随宿主状态更新，渲染本身不调用模型。操作活跃说明宿主观察到了执行，不等于已经产出有效成果。

## 中断之后，仍有继续推进的路径

长任务需要的不只是启动按钮。Agent Swarm 将分工、证据、决策和恢复状态保存到磁盘，支持在已覆盖的中断与重启场景中继续工作。

**返工保留原来的任务目标。** 任务被独立复核驳回后，主 agent 可以在原任务上返工：`swarm_control` 的 `action: "resume"` 会把被驳回的任务重新交给原作者（作者保持固定，从被驳回的 commit 继续修改），并以同一位复核人重新打开作出驳回的复核，因此重新提交后立即复核，不会新增复核任务。每个任务最多返工 `maxRework` 次（默认 2 次，可在 `swarm_control` 的 `changes` 中提高）；超出后，用 `replaces` 提出的替代任务对原任务须满足的全部验收条件负责，包括原任务在 `covers` 中引用的条件，且无需复制；下游依赖跟随已验收的修复，替代任务被验收时会退役它所替代的整条链。被驳回的 commit、驳回理由和该轮的声明作为归档历史保留在任务及其复核上：不能再次质疑，也不会阻止完成。主 agent 还可以在原任务上修订执行额度和未提交工作的计划，按新版本修复启动失败的保存计划，并在不改变工件的情况下为已提交工作追加检查。

**需要判断时，交回主 agent。** 审查驳回、工作受阻、供应商异常或预算耗尽等情况可以产生持久通知。主 agent 能调整计划、安排修复，或附带原因修改预算。常规恢复决策无需你重新配置团队。

**完成必须有依据。** 尚未完成的合成和复核会留在任务板上，并通知主 agent 修复。没有可运行任务，不会触发静默撤回必要工作或宣布完成。

**资源使用始终可查。** 主 agent 决定团队规模、任务上限、步数与 token 预算、恢复次数和验证超时。用量按团队记录，展示缓存和输出等明细，并单独列出主会话用量。继续任务不会重置已消耗的资源。原生 worker 会话需要重建时，持久化的会话计量代次会区分新旧水位，保留历史累计并继续记录新增用量。

恢复受任务预算与期限约束。主 agent 离线时通知会排队；卡住的原生模型调用也可能延迟消息处理。供应商用量上报和在途请求的估算，仍可能使实际用量超过预算。

## 产品架构

**主 agent 决定方向，运行时协调工作，Harness 执行智能体。**

```mermaid
flowchart TD
    G["你的目标"] --> P["主 agent · 计划、成员与预算"]
    P -->|计划与决策| R["Swarm 运行时 · 持久化协调"]
    R -->|需要决策的通知| P
    R -->|前置条件满足的任务| W["原生成员 · 并行协作"]
    W -->|提交成果与证据| V["独立复核 + 宿主检查"]
    V -->|验收结果或返工需求| R
    R -->|已验收的交付成果| D["查看修改 · 应用到项目"]
```

**明确规则之内，保留协作自由。** 成员可以共享证据、提出后续工作；运行时检查范围、依赖和复核要求。成员之间的消息不能扩大权限、提高预算或豁免独立审查。

**恢复属于协调过程。** 持久状态把任务与执行实例、成果、决策关联起来。执行中断后，运行时拒绝旧实例继续写入，并通过支持的检查点、重试或重新分配路径恢复。需要判断的情况交回主 agent；已验收的替代成果成为下游任务的新前置条件。

**原生执行，统一呈现。** Harness 提供模型执行、会话、收件箱、工具和沙箱。插件负责协作与验收规则，侧栏展示任务状态和观察到的活动。协作消息进入原生收件箱与会话记录，协调数据保存在 SQLite 中，无需修改或 fork Harness 核心。

实现约定与设计来源见[设计说明](docs/design.md)。

## 开始使用

Agent Swarm 当前以源码插件形式提供。你需要：

- **Node.js `^22.19.0 || >=24.0.0`、Git，以及 macOS 或 Linux。** 任务在本地 Git 仓库中执行。
- **已构建的受支持 DeepSeek Harness。** 只支持三个版本：`0.2.1-rc.2`（npm `latest` 与 `next`，默认宿主），以及较早的 `0.1.5-rc.3` 和 `0.1.7-rc.1`，准确提交见[兼容矩阵](compatibility.json)。用 `DSH_HARNESS_ROOT`（或 `DSH_SOURCE`）指定检出；未指定时，脚本依次查看 `~/.dsh/source/current` 和同级目录 `deepseek-harness-021rc2`、`deepseek-harness-015rc3`、`deepseek-harness-017rc1`，取第一个已构建（存在 `apps/cli/lib/bin.js`）的受支持版本检出，其他版本或未构建的检出会被跳过。
- **可用的 Harness 模型配置。** 凭据由宿主管理；除非计划指定其他模型路由，成员默认沿用主会话模型。

```sh
git clone https://github.com/TT-Wang/dsh-agent-swarm.git
cd dsh-agent-swarm
export DSH_HARNESS_ROOT="/absolute/path/to/deepseek-harness"
npm run link:dsh
npm run build
node "$DSH_HARNESS_ROOT/apps/cli/lib/bin.js" plugin --profile web add "link:$PWD"
```

从准备开展任务的项目目录启动 Harness：

```sh
cd /absolute/path/to/your-project
node "$DSH_HARNESS_ROOT/apps/cli/lib/bin.js" --profile web
```

打开 Harness 输出的已认证启动链接，在会话中选择模型，输入 `/agent-swarm` 加上自然语言目标即可。该命令已注册到原生命令补全中。

在两个受支持宿主上，Agent Swarm 都位于原生右侧栏，默认折叠。发送 `/agent-swarm` 加自然语言目标后会自动展开；也可以随时点击左侧导航底部的 Agent Swarm 按钮重新打开。右侧栏属于单个会话：打开某个成员的会话后，用同一个按钮打开它的只读协作视图。界面支持中英文和深浅主题。

Bundle 安装、升级、启动恢复与配置详见[使用与运维指南](docs/operations.zh-CN.md)。

## 适用范围与实际边界

- **本地执行。** 不支持分布式成员、非 Git 项目或 Windows 执行。多个宿主需要独立状态目录，不支持并发恢复同一数据库。保留的 worktree 与成果引用需要显式清理；崩溃遗留的验证检出目录由同一任务下一次运行声明检查的验证回收；git 在记录路径前留下的锁定注册需手动删除。
- **0.1.7 和 0.2.1 强制执行版本约束，0.1.5 不执行。** 0.1.7-rc.1 和 0.2.1-rc.2 会把插件固定的 `@deepseek-ai/dsh-*` peer 版本范围与正在运行的版本比较，不匹配时拒绝安装插件，并停用已挂载的插件行。0.1.5-rc.3 没有这项检查，插件在其他 0.1.5 或 0.1.6 版本上加载时不会被拒绝：在这些宿主上，受支持版本列表只是文档声明，并无强制。profile bundle 中的 `requires.harness` 在所有受支持宿主上都只是声明。
- **文件交付物。** 成员通过 `swarm_submit.deliverables` 列出准确的相对文件路径，独立复核报告可用可选的 `swarm_verify.deliverables`；即使被 Git 忽略，宿主也能只捕获这些明确文件，不修改源检出的忽略规则。提交回显绑定 commit 的 blob ID 和字节数，复核以固定源 commit 为准，主机检查在该版本的新检出中执行，作者后续覆写不会改变被复核的报告。同源复核改派会保留已保存草稿。已延期或驳回裁决的复核，交接的是其裁决捕获的记录；返工任务改派给其他成员时，从被驳回的提交开始；前一成员在裁决或提交之后写入工作区的内容不会被取用，该成员也不会被停止。每个任务还要声明 `outputs`，即它必须产出的文件：宿主会捕获每个声明的输出（即使被 Git 忽略），声明的输出缺失时以 `[output_missing]` 拒绝提交，交接时保留声明的草稿，未声明 outputs 的计划任务不能启动（`[]` 表示纯分析任务）；宿主不再从任务文字推断路径，既未声明也未列出的忽略文件不会被捕获；未声明的忽略文件不会自动收集，发生覆盖冲突时会停止切换工作区并提示路径。
- **可审查的证据。** 独立复核与宿主检查让验收有据可查，但无法保证所选检查覆盖所有要求。实际代码、配置改动即使标为 research 也需要宿主检查，已知报告格式则不需要代码检查；文件格式分类不等于程序语义分析。明确的空操作检查会被拒绝，但检查是否覆盖验收条件仍需独立复核人判断。owner 可以在已提交产物所属的原任务上追加检查，不必取消重建。升级不会追溯重审已有 accepted 历史。验证默认复制已有依赖及常见虚拟环境解释器，仍可能依赖宿主系统库。不支持的外部依赖链接需要改为自包含安装或由宿主显式授权；这不是全新的 CI 环境。
- **原任务返工。** 只有被自身独立复核驳回的任务可以返工；被驳回的实验任务，或提交后被判定失效的工作，仍需替代任务。作者的步数与恢复次数在多次返工间累计，额度用尽时 resume 会以 `task_budget_exhausted` 拒绝，需先提高额度；重新打开的复核每一轮都从全新额度开始。重新提交必须改变 commit 或带来新的宿主可验证声明，否则以 `[rework_unchanged]` 拒绝。被重新打开的复核所绑定的成员永远不能接手返工；若它是唯一仍在线的成员，任务会等待主 agent 增加成员或改派该复核。
- **宿主补充的复核。** 计划中没有配对复核的交付任务，会在启动、保存草稿以及列出旧版本保存的草稿时获得一个未分配的独立复核，并计入 `maxTasks`。只有当某个未停止的成员可以独立承担时，该复核才算有效的复核路径；因此若计划中唯一在线的成员都是交付物作者，提交后会以 `[review_path_missing]` 通知 owner。补充的复核不复制验收条件：它检查交付任务须满足的全部条件，覆盖字段中的 `acceptance` 只增加复核专用条件。省略的 `review` 覆盖字段依次默认为：未分配、宿主的复核目标、无额外验收条件、交付任务的 `maxRecoveryAttempts`，以及默认 `maxSteps`。
- **按编号引用验收条件。** 任务的验收条目依次编号为 `c1`、`c2`……，交付任务在 `covers` 中列出它满足的条件编号；计划中复核任务的 `covers` 会移到被复核的任务上，`swarm_propose` 拒绝复核任务携带 `covers`。新交付任务需要 `covers` 或自身的 `acceptance`，复核任务和替代任务两者都可省略。任务只保存自身的验收条件：执行者和复核人看到这些条件、它所覆盖条件的文字，以及它所替代任务须满足的全部条件。主 agent 在每个返回任务的地方（`swarm_propose`、`swarm_control`、`swarm_cancel` 的结果，`swarm_observe`，面板的快照以及 `swarm_registry`）读到的都是保存的任务本身：它自身的 `acceptance`、`covers` 和 `replaces`，编号对应的条件可在一次全新的 `swarm_observe` 概览中查到；执行者从不读到编号。完成判定只统计已接受交付任务引用的编号，包括它所替代任务引用的编号；复制的条件文字不算覆盖。`covers` 不能修改，因此未引用编号就被接受的交付任务，其条件只能由另一个引用这些编号的交付任务覆盖。草稿编辑器将验收条件列为带编号的行，为每个交付任务的每条条件提供“覆盖”勾选框，删除条件时会重新编号 `covers`；只有自动启动会拒绝没有交付任务引用的条件，因此从编辑器启动、留有未勾选条件的草稿可以运行，但在另一个交付任务引用该条件之前无法完成。任务一旦创建，验收条件即固定：修复已暂存的草稿时必须原样重发。早期版本写入的存储会在打开时一次性改写：每个已有任务和草稿中的计划任务只保留自身的验收条件（替代任务去掉从被替代任务继承的条件，复核任务去掉被复核任务已提供的条件），每个交付任务把复制的条件文字换成对应编号，并像重新启动那样把已保存草稿的验收条件写入已暂存的任务。这样改写过的已保存草稿会成为新的修订版本，因此升级期间一直开着的编辑页面会重新加载它，无法用旧副本覆盖这些编号。
- **工作区权限由人配置。** 任务使用会话所在工作区，或 `authorizedWorkspaces` 配置的根目录；匹配的授权记录为 `workspaceGrantRoot`。智能体不能通过 swarm 工具自行新增授权。执行边界沿用 Harness 沙箱，插件不额外提供网络或凭据隔离。
- **可观察、有边界的恢复。** 实时界面展示操作和事件，不提供逐 token 输出或保证准确的完成时间。恢复机制不承诺外部副作用恰好执行一次、任意磁盘故障恢复或整个文件系统上的原子应用。卡在慢速 worker 调用中的调度轮次会一直占住该任务，直到该调用在自身时限内返回；超过界限时会通知 owner，且仅在它仍然卡住时通知：该轮次返回后，owner 尚未读到的这条通知会被撤回，也不再提醒。
- **每个事实只通知一次。** 主 agent 对每个事实只收到一次通知，通知以引发该事实的依据为键（某个任务及其 epoch、一次复核需求、一个限额值、一次违规、记录它的事件），从不以整个看板的快照为键。条件结束后又以同一依据再次出现时不会重新通知：先前的通知重新变为待处理，只有该通知剩余的提醒（最多两次）会再提起它。停滞的工作总会被指明：只要各自的条件成立，停滞通知、任务整体停滞通知、派发问题以及指明无任何活动路径推进的工作的通知都会发送，即使某个决策已经指明了同一项工作。唯一较早的例外是：某任务在同一 epoch 的驳回已经通知了主 agent，且没有其他工作在等待它时，不再为它单独发送停滞通知。没有活动复核的提交只在运行时自己的复核步骤仍能为它接纳复核时（在短暂的宽限期内，或没有任何原因阻碍复核时）阻止任务被判定为停滞；派发问题会询问每个已就绪但未被派发的任务，每个 epoch 一次，并与其他通知并存，其他通知仍会指明看板上的其余工作。因此同一状况仍可能以措辞不同的多个事实通知主 agent，这是尚未解决的问题 R20：派发失败或隔离请求与派发问题并存；启动失败或成员停用与派发问题及停滞通知并存；工作目录授权被撤销时，工作目录请求（指明被阻塞的工作）与每个被阻塞任务的停滞通知以及任务整体停滞通知并存；任务上限或恢复请求与被它阻塞的任务的停滞通知并存；无法复核的提交与任务整体停滞通知并存，撤回某个复核而改变停滞的工作时还会再发送一次任务整体停滞通知。要让每个状况只有一种措辞，某条通知可能让位给的每个决策都必须恰好在其自身原因成立时保持待处理：其中若干原因（恢复上限、任务上限、收尾失败、工作目录授权撤销、准备失败、驳回）目前还没有可供绑定的持久记录；针对某个成员的请求会列出该成员所有未完成的工作；被让位的通知还必须在它所让位的决策结束后重新发出。在此之前，没有任何通知会为另一条通知让位，因此停滞的工作绝不会无人指明。通知密集时，后续事实会并入唤醒摘要，摘要列出每个任务，并指向带 `deliveryId` 的 `swarm_observe`，以读取完整事实及其出口。从旧版本升级后，仍未解决或再次触发的条件会以新的键再通知一次。
- **代码结构。** `src/runtime.ts` 仍是一个约 3,900 行的类。它构建的七个 seam（refusals、notices、attempts、工作区准入、声明检查、gates、scheduling）建立在它的 kernel 及其下层 seam 之上，没有一个导入 runtime，连类型也不导入；即使把仅由类型构成的导入也计算在内，src 的导入图中也没有循环。工作区引擎、notices、types 和 tools 尚未拆分（[已知限制](docs/known-limitations.md#code-structure)）。

详细约束与剩余风险见[已知限制](docs/known-limitations.md)，集成验证依据见[验证记录](docs/validation.md)。使用脚本化模型响应的测试不能当作模型质量或速度基准。
